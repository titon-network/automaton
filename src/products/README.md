# src/products/

The pluggable per-product registry. Every Titon protocol that wants operator-side action (Kronos, Fortuna, Themis, Phoebe, future Argus / …) implements `ProductModule` here. The orchestrator iterates `PRODUCTS` — `runDaemon`, `drainEvents`, `resolveDeployment`, `checkSchemaVersions`, `explainExitCode`, `doctor`, and `status` are all data-driven from this list.

| File | Purpose |
|---|---|
| `types.ts` | The `ProductModule` interface + `ProductWorker` + `ProductContext` types. Read this first before authoring a new product. |
| `index.ts` | `PRODUCTS` array (registration order = iteration order) + `enabledProducts(config)` filter. |
| `kronos.ts` | Poll-driven worker template. `KronosWorker` iterates the registry every tick, decides which jobs to execute, sends `Execute`. Use this as the base for products driven by polling on-chain state. |
| `fortuna.ts` | Event-driven worker template. `FortunaWorker` enqueues from `RequestCreated`, signs alpha with a BLS share, submits `FulfillRandomness` before the deadline. Use this as the base for products driven by inbound events. |
| `themis.ts` | Multi-chamber event-driven worker. `ThemisWorker` tracks per-chamber round + bid state from `RoundStarted` / `BidSubmitted` events; once the commit window closes, threshold-decrypts every cached bid (`D = sk · c1`), BLS-signs the reveal payload, submits `RevealRound`. Parent-child architecture: factory + chamber addresses live in the address bag (`atlas` / `factory` / `chamber:<addr>` keyed via `themisChamberAddrKey()`). v1 is solo-mode + static `config.themis.chambers`; auto-discovery + multi-op share-exchange are v1.1. |
| `phoebe.ts` | Heartbeat-pushed Merkle snapshot worker. `PhoebeWorker` builds a `PhoebeMerkleTree` from `config.phoebe.feeds[]` once per `pushIntervalMs` window, BLS-signs `computeSnapshotHash(phoebeAddress, timestamp, root)`, and submits `PushSnapshot`. Solo when `peers` is empty; otherwise threshold-additive via `daemon/share-exchange-phoebe.ts` (POST `/phoebe/v1/share`, port 9092). Timestamps are rounded to `pushIntervalSec` window boundaries so operators with synchronised clocks sign byte-identical messages without out-of-band consensus. Feeds can be **static** (`{mantissa, expo, confBps}` — testnet) or **dynamic** (`{sources: [{name, symbol}, ...]}` — production, aggregated live from `phoebe-sources/`). Operators using dynamic feeds MUST configure the same source list across the group so medians line up. |
| `phoebe-sources/` | v2 price-source layer for production-grade dynamic feeds. `PriceFeedManager` owns the latest-tick cache + median aggregator; per-exchange adapters (`binance.ts` / `coinbase.ts` / `kraken.ts` / `stonfi-twap.ts`) inherit from `ws-base.ts` for hardened reconnect (per-attempt connect timeout, silence-timeout reconnect, pong-deadline, equal-jitter backoff with stable-uptime reset, persistent-failure escalation to error log after 10 consecutive attempts). Worker calls `manager.aggregate(feed)` per push window; insufficient-source feeds drop from the snapshot rather than sign stale data. **Security defenses in ws-base + parse + manager**: ws `maxPayload` capped at 1 MiB + `perMessageDeflate: false` (zip-bomb defense); `parsePositivePrice` caps input at 32 chars (BigInt O(n²) DoS); rescale shift capped at 24 places (hostile expo defense); subscribed-symbol allowlist drops ticks for symbols the operator didn't subscribe to (cache-OOM defense); local-clock receivedAtMs (server-supplied timestamps could bypass staleness checks). `setWsCtor` is a test-only seam and NOT re-exported from the public barrel. |

See [`../../CLAUDE.md`](../../CLAUDE.md) §"Adding a new product" for the three-line addition guide. The orchestrator integration is documented in §"AI navigator" under "Wire a new consumer product".
